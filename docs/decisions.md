## 2026-09-26 — B1.1 Audit chain and authentication

15. **AuditLog** is append-only with a per-hotel `seq`; `hash = sha256(prev_hash + canonical_json(payload))`, payload = seq, hotel_id, actor_id, action, entity, entity_id, before, after, at (UTC ISO). Canonical JSON: sorted keys, no spaces, UTF-8 kept. `before/after` are stored after a JSON round-trip, so verification hashes exactly what is stored. Unique (hotel_id, seq) makes a concurrent writer fail rather than fork the chain. Passwords and PIN hashes are never copied into audit rows.
16. **Action names** are `<entity>.<verb>` (`user.update`, `auth.login_pin`, `system.clock_rollback`). Every service calls `audit.record()` inside its transaction.
17. **Login** follows the login artboard: public `GET auth/users` for the user picker; wrong PIN returns 401 with `attempts_left`; the 5th failure locks for 5 minutes (423 `account_locked` with `locked_until`) and is audited; a manager can lift it (`POST users/:id/unlock`). PIN and password share the failure counter; password confirmation also counts.
18. **Session**: DRF token, one per user (new login replaces the old), expires 12 h after login (`token_expired`). Session auth stays on for the browsable API.
19. **Confirmation token**: `POST auth/confirm {password}` → signed, user-bound token valid 5 minutes, sent as `X-Confirm-Token`. Required for create/edit user, reset PIN, clock approval (and later: prices, checkout with debt, rule delete/disable, import, big discounts).
20. **Roles**: managers manage reception and manager accounts; only the owner manages owner accounts. Nobody can deactivate themselves or change their own role. Deactivating a user revokes their session. Manager and owner accounts need a password; reception accounts may be PIN-only.
21. **Clock guard**: detection and approval are audited (`system.clock_rollback`, `system.clock_approve`); `POST system/clock/approve` needs manager + confirmation. `/api/v1/auth/*` stays reachable while blocked so a manager can sign in.
22. **Coverage gate**: CI fails if any `apps/*/rules.py` is below 100 % line coverage.

## 2026-09-26 — B1.4 Reservations

34. **Durations**: daily ×N = N nights, weekly ×N = 7N, monthly ×N = 30N; `check_out_date = check_in + nights` (exclusive); `last_night` is returned for the «تنتهي بنهاية يوم …» text. Max 366 nights.
35. **Pricing options** (spec §6.1): weekly and monthly are exact; daily stays of 7+ nights also offer months→weeks→nights and weeks→nights mixes, deduplicated and sorted cheapest first (10 nights → «أسبوع + 3 ليالٍ» 113,000 / «10 ليالٍ» 120,000, as on artboard 6.4 B). With several options the client must send `option_key` (400 `pricing_choice_required` lists them). Labels use Arabic number agreement (ليلة / ليلتان / 3 ليالٍ / 30 ليلة).
36. **Rate snapshot** stores the type name, the three prices, the chosen option and label, base total, and any override with its reason; `Reservation.total` is the agreed room charge. A price override needs a reason (artboard: «سبب تعديل السعر *»). Discounts, deposits and payments come with folios in B2.
37. **Overlap** (spec §6.2): confirmed and checked-in reservations block their room over [check_in, check_out); a checked-in stay also holds the room through today when overdue. Booking locks the room row (`select_for_update`, row lock on PostgreSQL; the IMMEDIATE transaction serializes on SQLite) before checking. Verified by a 6-thread race test on a real SQLite file: exactly one wins.
38. **Room checks at booking**: out-of-service rooms are refused; rooms under maintenance are refused only for arrivals today (a future booking may be made while repairs finish). Past arrival dates are refused (the opening-day migration will use `allow_past`).
39. **Tests use a SQLite file** (in the test `SKYTOWERS_HOME`) instead of in-memory, so they exercise WAL and real locking.
40. Reservation cancel (before check-in) needs a reason; no-show only from the arrival day; a room can be assigned later with the same overlap check.

## 2026-09-26 — B1.5 Stays and the room board

41. **Check-in** from a confirmed reservation between the arrival day and the last night (late arrivals keep their dates); the room must be ready and free; opens `Stay` + first `StaySegment`. **Walk-in** («تسكين الآن») is `check_in_now: true` on booking: reservation and check-in in one transaction.
42. **Extend** adds nights after the current end at the room type's *current* prices (artboard 6.5 D: «السعر الحالي»), with the same option/override rules as booking; same kind accumulates the count (monthly ×1 + ×1 = monthly ×2), otherwise the booking becomes `mixed`. The extension is appended to `rate_snapshot.extensions`.
43. **Change room** takes effect today: the current segment closes today, a new one opens; the vacated room goes occupied → cleaning (→ maintenance if chosen, with reason); the new room must be ready and free for the rest of the stay. Price difference = booking priced at the new type minus the old type, pro-rated over remaining nights, rounded to whole pounds; negative needs a manager override (V2 artboard 6.5 E). Candidates list same type first.
44. **Manager override** = the manager's password typed on the reception screen plus a reason (artboards 6.5 C and 6.5 F). The server matches it against active managers/owners and records the approver on the stay and in audit. Failed override attempts are not yet rate-limited (to add with B2 checkout-with-debt).
45. **Checkout** closes the segment on the actual departure day (early or overdue) and sends the room to cleaning or maintenance. The balance ≠ 0 rule and debt recording arrive with folios in B2; the override fields are already accepted and recorded.
46. **Cancel stay** needs a reason and a manager override; settlement options price the nights used (at least 1) at the booking's prices, same decomposition logic as booking (V2 artboard 6.5 F: «12 ليلة» vs «أسبوع + 5 ليالٍ»), or a manual total. Status becomes `cancelled`; nothing is deleted; the previous and new totals are kept in `rate_snapshot.cancellation`. Refunds come with payments in B2.
47. **Room board** is `GET rooms?view=board`: every room with its stored status, a derived `display_status` (overdue), current stay (guest, last night, `days_left`), next booking, and a summary (occupancy over in-service rooms, arrivals/departures today, overdue, counts by status). `balance` is null until B2.
48. **Seed** loads the 18 occupied rooms of the Room Board as checked-in stays and the 102 booking, dated relative to the day it runs; it reproduces «18/30 · 60٪», two overdue rooms and two departures today.
49. Removed `# fmt: skip` markers everywhere; code layout is left to `ruff format`.

## 2026-09-26 — B2.1 / B2.2 Cash, folios and payments

50. **One PR for cash and billing**: shift totals need payments and payments need an open shift, so the two slices ship together.
51. **Shift** = one open per device (`config.json` `device_name`, default the computer name), enforced by a partial unique constraint and a 409 `shift_already_open`. Expected cash = opening + Σ cash payments − Σ cash expenses (bankak/transfer never enter the drawer), stored at close with the counted amount; a difference needs a reason (400 `reason_required` with `difference`). The closer may differ from the opener (`closed_by`). `shifts/current` returns totals by method, movements (open, payments, expenses) and the last closed shift.
52. **Expenses** are append-only: categories as on the artboard (مستلزمات، مشتريات، صيانة، فواتير، رواتب، أخرى); every expense (any method) belongs to the open shift; a mistake is corrected by a reversing row with a reason in the current shift. Receipts above the hotel threshold (default 20,000) are *flagged* `attachment_missing` («بانتظار مرفق»), not blocked; photos can be attached later (compressed like ID images, shared `apps.core.imaging.store_image`).
53. **Hotel settings** (V2 «بيانات الفندق»): names, address, phone, digits, money decimals, stay day end, session lock, expense receipt threshold, max discount %, thermal printer, auto-print. `GET/PATCH system/settings` (PATCH manager, version-checked, audited).
54. **Folio per reservation** (deviation from spec §5 "Folio | stay 1:1"): deposits («عربون») are taken at booking, before a stay exists (artboard 6.4). The folio is opened at booking with a gap-free invoice number (`Sequence` row locked and bumped in the same transaction; a rollback returns the number). Receipt numbers use the same mechanism.
55. **Lines**: room charge posted at check-in («إقامة شهرية — مزدوجة 203 (30 ليلة)»), booking discount posted with it, extensions as room lines, room-change difference as an adjustment, cancellation as an adjustment down to the settlement total (discounts included; service lines kept). Service charges and discounts can be added later; any line can be reversed once with a reason.
56. **Discounts** need a reason; up to `max_discount_percent` of room charges needs no manager, above it a manager override (password + reason) — at booking or on the folio.
57. **Payments** always go into the open shift; bankak/transfer need a reference; before check-in they are deposits. Mistakes are reversed with an opposite row in the current shift (red «عكس دفعة» line pointing to the original). Refunds cannot exceed the guest's credit.
58. **Checkout** with balance ≠ 0 → 409 `balance_not_zero` with the amount; a manager override lets the guest leave and the balance stays on the closed folio (debt report). Payments on closed folios are allowed (paying a debt later). **Stay cancellation** refunds any excess automatically in cash from the open shift (V2: «يُسجَّل كردّ نقدي من الوردية»).
59. **Board** shows each stay's folio balance and invoice number (two aggregate queries for all rooms).
60. **Seed** puts earlier payments in a closed back-office shift (bankak, so the drawer is untouched), leaving the brief's balances (203: 15,000, 305: 42,000), then opens today's shift (أحمد علي, 50,000) with the two expenses of artboard 6.8.

## 2026-09-26 — B2.3 Reports, exports and print data

61. **Report shape** (spec §7): `GET reports/<name>` → `{name, columns[{key,label,type}], rows, meta{title, as_of, date_from, date_to, formula, note, tiles, totals}}`; money stays in minor units. `GET reports` lists them with a red `badge` count (debts, overdue, shifts with a difference this week) as in the V2 report index. Ten reports: occupancy, arrivals_departures, current_guests, ending_soon, debts, revenue, expenses, cash_shifts, adjustments, room_status. «الاستجابة للتنبيهات» arrives with the alert engine (B3).
62. **Occupancy** follows artboard 7.3: a room is occupied for a night if a stay is in progress at midnight (overdue guests count until checkout); maintenance = status at end of day from the status history; % = occupied ÷ (in-service rooms − maintenance). Revenue = folio lines posted that day (charges, discounts, adjustments, reversals); collected = net payments that day.
63. **Debts** = folios of in-house or departed stays with balance > 0 (tiles: in-house, after departure, average/oldest age, month collection rate); `status=late` lists debts settled after departure.
64. **Exports**: `reports/<name>/export?format=xlsx|csv`. XLSX: right-to-left sheet, title and period rows, bold frozen header, money as numbers in pounds (0 or 2 decimals per hotel setting), percent/date formats, totals row, formula line. CSV: UTF-8 with BOM, comma, CRLF. DRF's own `?format=` switch is disabled (`URL_FORMAT_OVERRIDE = None`).
65. **Print data** endpoints feed the SPA's print pages (spec §8): `folios/:id/invoice` (7.1), `payments/:id/receipt` (7.2, amount in Arabic words «خمسة عشر ألف جنيه»), `expenses/:id/receipt` (7.2, gap-free `EXP-000123`), `shifts/:id/statement` (7.3). The invoice shows the guest's full ID number: it is the guest's own document (artboard 7.1), unlike the reception screens.
66. **Arabic amounts in words** (tafqit) up to billions with correct dual/plural/accusative forms; the counted word drops its tanween before «جنيه».

## 2026-09-26 — B3 Follow-ups, alert engine, clock-guard tick

67. **Rules** (artboard 6.11): one row per stay type with first alert `days_before`, optional `second_days_before`, `at_time`, `repeat_hours` (after the last scheduled alert), `max_snoozes` (3), `escalate_after_hours` (24), Windows toggle, active. Defaults seeded on first tick: daily = day of end, every 6 h; weekly = 2 days before + day of end, every 12 h; monthly = 5 + 2 days before, every 12 h; overdue (every 24 h); checkout with debt (> threshold 0); shift open > 14 h; cleaning > 4 h; maintenance > 7 days; no backup > 24 h and no Drive upload > 3 days (generators arrive with B4). Mixed stays follow the daily rule.
68. **Tasks** are unique per (rule, subject, due date) — subject is `stay:`, `room:` or `shift:` — so ticks are idempotent and catch up after the PC was off with the *original* `due_at` (one notification, not one per missed slot). A stay booked with less lead time than the rule alerts from check-in.
69. **Actions** (artboard 6.6): extend (runs the stay extension), confirm departure (runs checkout, incl. override), awaiting reply (note + follow-up time, required), snooze (until a time; refused at the limit with 409 `snooze_limit`), done (note required). Only an action closes a task; every action is a `TaskAction` with the open shift and an audit row.
70. **Escalation**: a task still open `escalate_after_hours` after its due time becomes **neglected** and records the shift open at that moment («مُهمَلة — وردية: أحمد»).
71. **Supersession**: extension, room change, checkout and cancellation mark the stay's pending tasks `superseded` (with the reason); the engine plans fresh ones from the new end on its next tick. Nothing is deleted.
72. **Toasts** (artboard 6.6 B): title «غرفة 305 — متجاوزة منذ يومين» (≤ 40 chars), body «محمد عثمان · شهري · انقر للفتح»; queued at first alert, second alert, then every `repeat_hours`, and when a snoozed/waiting task returns. The tray polls `followups/toasts?after=<cursor>`.
73. **Board** (`followups/board`): متأخرة (stay past its end), اليوم (due tasks), القادمة (in-house stays whose first alert is still ahead, with the planned time), system tasks; one row per stay. `tasks?status=open&count` feeds the login/top-bar badges.
74. **Scheduler**: `service/scheduler.py` runs `engine.tick()` every 60 s in a daemon thread started by `run_waitress` on the reception role; the tick first runs the clock guard and does nothing while it blocks. `manage.py run_engine [--once]` for manual runs.
75. **Report «الاستجابة للتنبيهات»**: per task — first action, response time, snoozes, result, who, neglected shift; badge = neglected tasks.

## 2026-09-26 — B4.1 Encrypted backups, owner read-only, merge import

76. **Backup file**: `VACUUM INTO` copy of the live SQLite DB (SQLite-only by nature; PostgreSQL would use `pg_dump` in the same module), attachments (all on the weekly full, else changed since the last full), `manifest.json` (hotel, seq, created_at, schema/app version, applied migrations, audit seq, SHA-256 per file), zipped, encrypted with age (`pyrage`) to the owner's public key, named per spec §9.1. Written to `backups/` and the optional second folder (a missing USB disk is reported on the run, not a failure), then retention (keep N).
77. **Backup runs** (`BackupRun`, append-only device records) cover manual, scheduled (every `interval_hours` from the scheduler thread) and shift-close backups (after the closing transaction commits). A scheduled/shift-close run with no new audit rows is recorded as skipped («لا تغييرات منذ آخر نسخة»). Backups do not write audit rows, so they do not count as changes. A missing owner key fails visibly. `no_backup` alert after 24 h.
78. **Owner key**: `manage.py generate_owner_key` on the owner PC creates the age identity under `SKYTOWERS_HOME/keys` (DPAPI-wrapped on Windows) and prints the `age1…` public key for the reception's backup settings.
79. **Owner PC is read-only** at the API: `OwnerReadOnlyMiddleware` refuses every write except `/api/v1/auth/` and `/api/v1/owner/` with 403 `owner_read_only`. The owner PC never writes audit rows (the chain belongs to the reception and arrives by import; a local row would collide with imported sequence numbers). Login bookkeeping (failed attempts, lock, last login) uses row updates that do not bump `version`/`updated_at` — a login is not an edit, and on the owner PC a newer `updated_at` would hide the reception's real edits at the next import.
80. **Merge import** (spec §9.3) runs the five checks of artboard 6.13 C — التوقيع (decrypt + SHA-256 of every file), سلامة القاعدة (`PRAGMA integrity_check`), معرف الفندق (first import adopts it into `config.json`), الإصدار (refused if the backup has migrations this app does not know), سلسلة التدقيق (hash chain intact; an older sequence than the last import is a warning that needs «متابعة رغم ذلك») — then attaches the copy as the `incoming` alias, migrates it, and merges in dependency order in one transaction: append-only tables insert absent rows; mutable tables insert absent rows and update only where the incoming `updated_at` is newer. Incoming timestamps are kept as-is (auto_now is suspended during the merge). Device state is not merged (clock, sequences, tokens, backup runs/settings, toasts). Any failure → failed `ImportRun` with the checks, no local change.
81. **First import on an empty owner PC** needs no login (there are no users yet); after that importing needs a manager. `manage.py import_backup <file>` does the same from the command line.
82. **Property test** (Hypothesis): random bookings/payments/expenses/extensions/checkouts with backups at random points, imported in random order with repeats → owner totals equal reception totals. Verified to fail when the timestamp preservation is removed.
83. **Windows**: the `incoming` SQLite file is closed before its temporary folder is removed (Windows cannot delete an open file). CI runs steps in bash on both OSes and turns pytest failures into GitHub annotations (`build/junit_annotations.py`), readable through the REST API when job logs are not.
